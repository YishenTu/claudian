# Collab application domain

## Host installation authority

- Project membership owns Member identity, role, credential, personal ref, and the Member-level `hostOwnership.ownsAuthority` flag. None of those fields identifies the installation allowed to operate local Host authority.
- `HostInstallationBindingService` is the sole policy owner for local Host execution. It interprets the current installation against the authority marker, admits explicit legacy claim and transfer-target binding, and rejects mismatched Host-owned recovery before side effects. LAN Host start performs legacy binding before durable restart guards; its guarded authority-open callback may only use the service's already-admitted marker-capability revalidation path.
- `CollabLocalProjectRepository` owns bounded marker and authority-directory filesystem mechanics. Marker inspection is read-only; opening, creating, retiring, or removing authority state requires an owned capability issued for the current installation.
- Host runtime CA and process-lock state is scoped below `.claudian/collab/installations/<installationKey>/`. Legacy global CA files are read-only migration input during an explicitly approved legacy claim; global CA and lock files are never runtime ownership evidence.
- A synchronized installation with the same Host Member but a foreign marker remains an ordinary LAN client with the same role and credential. Local Host selection, recovery, TLS, locking, authority access, and deletion require `hosted-here`; Member authorization rules continue to use membership.
- Marker inspection failure is strict for Host-control operations, but it only makes the optional active-local target ineligible for ordinary LAN client routing. Project summaries isolate the affected Host projection as needs-attention instead of failing unrelated Projects.
- Only physical LAN Project setup, physical Host-transfer recovery, physical production authority-transfer preparation/recovery, private Cloud-bootstrap transition, and retirement tombstone records carry an installation owner. Cloud Create/Join, nonphysical authority-transfer requester/Manager intents, generic Publish, request, conflict, working-copy, Leave, claimant, and ordinary Member recovery remain synchronized client state.
- After a schema 2 marker exists, Host admission first reruns idempotent binding for eligible legacy source records before restart guards. Ownerless legacy target or terminal records remain visible and fail with recovery-required diagnostics; only valid foreign and completed owner-bound records remain inert synchronized evidence.
- Incoming Host transfer and Cloud-to-LAN target recovery persist an owner-bound intent before listener, TLS, staging, or provisional authority work. Cloud-to-LAN keeps the canonical authority directory markerless until relinquishment proof; activation binds only an exact, complete provisional database and repository.
- A hosted route becomes visible only after its project is live with the installation-scoped pinned CA. Every hosted-route publication, removal, or rebind resets the shared LAN work-session projection after route visibility changes so cached clients cannot retain a stale local route.
- A reconnectable LAN control failure coalesces uniquely trusted discovery at the shared work-session boundary, persists endpoint and Git-origin rotation, resets that session generation, and retries the same idempotent operation once. Publish and review validate control and execute Git from one generation.
- Host start/rebind, reconnect, physical Host transfer, and Project authority convergence share one per-Project projection-transition lane for Git-origin plus membership changes. Extend and rename the existing lane when broadening its authority kinds; never retain parallel LAN and Cloud queues. Each writer revalidates its expected membership inside that lane before rotating origin and saving membership. Fresh Host clones have no stopped-Host origin; the first trusted route establishes it, while legacy sentinels are repair input only.

## Cloud client state

- Cloud has no deployed legacy binding population. Accept only the current Cloud binding and private record shapes; do not add old Cloud migrations or translate development identity into a production binding. Real LAN membership, setup, credential, Host and terminal-data migrations remain supported.
- Cloud native Create/Join own one durable admission intent in the existing pending-Project catalog, discoverable before the Project index exists. Persist exact endpoint, request/key, captured Projects folder/slug and staging ownership before a possible mutation. Finalize from a matching authenticated server response/snapshot, never an inferred Member, Host or generation.
- LAN Join and Cloud entry share the actual clone, validation, placement and new-working-copy finalization owner. Absorb those mechanics from Join rather than delegate Cloud setup to LAN admission or retain two algorithms. Membership, publication state and index must agree before admitting the ordinary session; surviving local publications are never reset by entry recovery.
- `CollabMembershipService` owns one bounded private Cloud user-mutation slot with the exact frozen request/key and retained result. UI close or response loss does not settle it. Automatic responsibility ACK/decline remains a separate durable receipt in `ManagerResponsibilityOperationCoordinator`, following the existing cache then role/cursor then receipt ordering; it never waits for the user-mutation slot or a manual acceptance ceremony.
- LAN-only Host/CA departure tuples do not apply to Cloud. Cloud pending Leave distinguishes a queued local choice from a submitted immutable wire request. The Vault journal survives index/private-state cleanup, and submitted replay cannot require an active snapshot, Project directory or Native Git. Fresh preparation binds authenticated identity, authoritative membership revision/Manager set and the exact advertised personal ref.
- `CloudRetirementClient` owns Cloud request intent until durable terminal handoff to the existing retirement handler. It never borrows LAN Host retirement intent. Submitted replay precedes active snapshot lookup, and terminal response/event/fallback use the same handler without nested lifecycle acquisition or draining the requesting session from itself.
- A completed rejection permits a new Leave preparation, Retire intent or pre-ID Manager transfer begin only after the owning authenticated state reads and recovery barrier prove the original operation cannot remain nonterminal. Error codes, elapsed time, missing files or an inaccessible authority are not that proof. Retire and Manager begin require a fresh explicit user intent/key after rejection; ambiguous requests remain frozen.

## Dependency direction

- `src/main.ts` resolves the installation key once and injects it into Collab composition. App and feature modules do not read renderer persistence directly.
- Core and presentation may consume the installation-status projection and explicit legacy-claim port only. They do not import the binding service, local repository, TLS identity, or Host coordinator.
