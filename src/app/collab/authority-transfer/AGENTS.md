# Project authority transfer

## Ownership

- This scope owns production LAN-to-Cloud and Cloud-to-LAN phase policy, source/target orchestration, semantic checkpoint capture/import, transfer-claim custody and redemption convergence, authority-generation movement, cancellation, terminal settlement, and restart recovery.
- Persist Project-local transfer records and operation-owned artifacts through `CollabLocalProjectRepository`. Register startup enumeration and recovery through `CollabProjectLifecycleSubsystem`; do not create a second Vault catalog, lifecycle subsystem, Project index, or physical-state owner.
- Reuse Project admission tokens, work-session drain/reset, Host start guards, origin and membership replacement, index reconstruction, retirement handling, and local Keep/Delete cleanup through their owning seams. Do not mutate their files or infer completion around them.
- `bootstrap/` remains a private two-client development fixture. `HostTransferPackage` remains physical LAN-to-LAN Host handoff. Neither is a production transfer transport, checkpoint, claim, or recovery mechanism.
- Before Host acceptance changes Project admission, acquire the existing `CollabProjectLifecycleSubsystem` per-Project lifecycle arbiter and re-enter it during every recovery attempt. A nonterminal physical Host transfer, Leave/cleanup, Retire/acknowledgement, private bootstrap, Manager-responsibility handoff, or another authority transfer must settle through its own owner or block; coordinator-local inspection never cancels or bypasses it. `ProjectOperationAdmission` supplies the later ordinary-work drain/suspension token but is not the lifecycle arbiter.
- One logical private `authority-transfer-entry` aggregate owns installation-keyed requester intents and the singleton installation-owned source/target responsibility. Persist each component in its own atomically replaced file so synchronized installations never rewrite an unrelated component; unexpected sibling or conflict files fail closed. Update and expire only the exact component while preserving the others. Requester components never own lifecycle admission, and foreign source components are observations rather than local durable owners. A requester whose proposal response was lost may adopt only the exact matching synchronized source observation before replaying the LAN request. The existing physical transfer record alone owns canonical transfer phases. Persist the exact successor before marking its owning entry component handed off; restart links Project, installation, operation, transfer and target or fails closed. A Manager observer settles before claimant admission and never remains a second nonterminal owner after handoff.
- `AuthorityTransferEntryService` is the sole feature-facing authority-transfer entry. It validates user selections, projects only public descriptors, handles and status, and delegates durable phase work to this scope's existing owners; core and presentation never receive transfer journals, proofs, credentials, caller-authored CAS facts or listener tokens. Exact concurrent LAN-to-Cloud acceptance shares one retained application operation, while cancellation of one caller detaches only that wait. The service retains its Cloud session and route-cleanup ownership until terminal settlement or shutdown.

## Authority and identity

- Any authenticated active LAN Member may propose one exact validated raw Cloud URL and stable intent. The LAN source owns the proposal, actual actor and replay; proposal-only construction must not create a Cloud connection or quiesce the source. Only the current LAN Host installation may accept that exact persisted proposal, settle pending admission, quiesce, capture, upload, retain claim custody, and commit source relinquishment, using its own operator-provided Cloud connection. Presence is never consent or identity proof and all-online participation is never required.
- Derive every internal child-operation idempotency key from the accepted intent with one bounded, operation-tagged digest. Never append to the caller's opaque ID because a valid maximum-length protocol value must remain executable and distinct across child operations.
- LAN-to-Cloud initially binds only the source Host through the accepted source proof. Cloud-to-LAN initially binds only the selected target Host through its provisional authority and locally generated credential. Every other imported active Member remains unbound until exact claim redemption.
- Before cutover, the source durably retains the complete raw claim batch and the target durably acknowledges its exact digest. Batch acknowledgement proves custody only. A source-held claim is scrubbed only after the same former Member forwards an exact target-signed redemption receipt or after bounded expiry.
- A completed LAN-to-Cloud source with an exact empty claim batch has no terminal responder work. After Cloud convergence, expire that responder immediately, remove only its operation-owned staging, custody, and exact requester entry, and release its route. Preserve the permanent physical fence, but allow a later Cloud-to-LAN Manager observer to coexist only after that exact predecessor is completed, its responder is expired, its terminal cleanup is durable, and no custody remains.
- A LAN claimant generates and durably stores its own credential before submitting only its hash. Claims never authenticate Cloud ingress, issue credentials, create membership, choose roles, move refs, or bind a different Member.
- Claimant recovery is reconstructed by the app composition from the surviving local membership plus the claimant record. Cloud-to-LAN records retain only the public pinned LAN target endpoint and CA trust needed for restart; no claimant operation may depend on a previously bound live runtime. Source-issued recovery resolves only the transports still authoritative for the durable phase: full source and target before redemption, target-only after source acknowledgement is no longer required, and local-only after target membership was committed. At source-issued expiry, pre-redemption records are scrubbed without remote replay, while a completed target redemption recovers forward through local convergence without retrying the expired source acknowledgement. A membership-converged record is terminal cleanup and never resolves a transport.
- When a different-device Cloud-to-LAN Manager uses the source-issued claimant path, `AuthorityTransferModule` alone validates the exact terminal Manager-to-claimant handoff. The Manager entry binds the initiating installation and Member, remains a nonterminal lifecycle owner in every surviving phase until its exact claimant is durably present, cannot be replaced or expired during that gap, and transfers admission ownership only to that claimant. Generic recovery never replays a foreign Manager entry; only target-owned physical recovery may observe its matching status. The claimant durably carries that exact Manager predecessor and initiating installation so synchronized recovery never depends on Manager-file delivery order. A synchronized non-Manager target records the completed Manager status but never creates, resumes, completes or removes that predecessor or claimant; its foreign claimant observation is not a local lifecycle owner and cannot block target physical recovery. Only the initiating Manager installation with its matching local Member and personal ref may perform claimant effects. A later target-side role change does not transfer or revoke that durable cleanup ownership. Completion removes the matching terminal Manager entry before removing the terminal claimant record. If Manager cleanup fails after membership convergence, retain the claimant proof so restart can finish both cleanups locally without the relinquished Cloud source or its scrubbed claim.
- Manager-reissued claims are a distinct variant in that same claimant owner, with their own transfer identity, target generation, validity interval and frozen redemption request. They never fabricate original source status, fetch or receipt acknowledgement. Persist a decoded target receipt before convergence and recover durable success forward after expiry. If an ambiguous response crosses the override's own expiry, only authenticated exact existing-Member binding plus completed transfer status can establish existing-binding recovery; otherwise remain visibly blocked, without inventing a receipt or ordinary Join.
- Cloud-to-LAN may select any active Member's installation, including a non-Manager. The target authenticates its identity and persists installation-owned preparation before TLS/listener effects, then persists the actual endpoint and public trust before sharing a descriptor. The Manager freezes begin before send and persists the returned transfer ID before sharing its handle. After begin, use exact transfer status and verified imported checkpoint identity, never an ordinary active-source snapshot or caller-manufactured acceptance proof. The journal, not a modal, owns the existing listener token and immutable published endpoint. Before proof can escape, withdrawal releases only target preparation; Cloud cancellation remains Manager-owned. Possible acceptance retains endpoint/proof until proved cancellation/invalidation or forward recovery.

## Lifecycle and recovery

- Existing authorities begin at generation `1`; the target activates at exactly `source + 1`. Before source relinquishment, cancellation must prove the target did not accept the fence. At or after relinquishment every owner recovers forward and no Host start or local recovery path may reopen the source.
- Host acceptance closes invitation and Join admission, revokes live invitations, and settles recoverable pending Joins through their owner. Divergent or ambiguous pending state blocks transfer and is never serialized.
- Logical checkpoint production excludes SQLite bytes, credentials, invitation secrets, CA private keys, working trees, unpublished files, caches, and local-only drafts/commits. Capture binds one quiesced authority snapshot to the exact allowed repository ref/OID inventory and package-owned manifest.
- Raw claim batches, checkpoint artifacts, and target staging are permission-restricted operation-owned state with durable intent before creation and exact cleanup on allowed cancellation, completion, or expiry. Never persist absolute paths in the transfer record or log content, claims, credentials, endpoints, or Git output.
- Source keys, proofs, manifests, and target private state use permission-restricted temporary files, file synchronization, atomic promotion, final-file validation, and best-effort parent-directory synchronization where the platform permits it. A restart removes or replaces only the exact operation partial and never treats a partially written final artifact as durable success.
- LAN Host acceptance atomically pins the live source-active route and durably records that exact endpoint before transfer work begins. The endpoint remains immutable through every owned LAN-to-Cloud phase and is the only endpoint on which source-active or terminal-source recovery may bind. An ambiguous post-save result retains the runtime pin; proven pre-fence cancellation releases it.
- The handed-off LAN source entry durably distinguishes Cloud begin not sent, possibly sent, and authoritative Cloud absence. Mark possibly sent immediately before the first begin request. Only not-sent or durably proved-absent state may complete cancellation locally; an ambiguous begin remains exact-replay recovery.
- Persist the exact Host cancellation request before any Cloud cancellation call and mark its submission possibly sent immediately before the call. Exact restart and user replay reuse only that tuple. If Cloud definitively rejects the tuple after revealing a later canonical phase, persist that forward status before clearing only the exact rejected cancellation; ambiguity retains it. A locally proved pre-begin cancellation checkpoints target cleanup, physically reopens the source, and only then records `source-reopened` and terminal cancellation; its recovery never opens a Cloud session.
- A stopped LAN Host may cross the temporary authority-transfer restart fence only through the exact locally owned cancellation record and its linked source entry. This cancellation-only restart remains subject to Host-installation, retirement, and bootstrap guards; ordinary Host start remains fenced.
- Completed LAN-to-Cloud source recovery restores the terminal responder on its durable source endpoint and converges any surviving LAN Host membership before it is considered settled. After durable responder expiry, recovery first converges that membership offline from the exact completed status and relinquishment proof, then performs local cleanup; it never requires the former Cloud target to be reachable.
- Cloud-to-LAN recovery prepares the listener directly against the durable target URL; it never opens an unpinned fallback listener first. Once the target entry hands off, physical-journal recovery reconstructs only a transfer-scoped Cloud connection whose Project, Member, personal ref and authority generation match that exact entry, and propagates the owning recovery cancellation signal through connection negotiation. It never falls back to an ordinary Cloud session or snapshot preflight. Completed target recovery validates the exact signed target proof and reconstructs activation, membership convergence, target-active routing, and Host startup only from operation-owned local state. It never requires the relinquished Cloud source to be reachable. Replaying the same durable target-active transfer is idempotent, including recovery after membership was committed but index reconstruction or Host startup failed.
- While the exact completed target-private state still owns recovery, it may repair only the known interrupted-import credential encoding by replacing the exact decoded-byte hash with the canonical credential-string hash for the proved target Host Member. A canonical hash is idempotent; any other existing hash, identity, generation, or binding conflict fails closed. This is in-flight recovery for the current transfer contract, not a general schema or legacy-format migration.

Kill recovery after every durable phase and prove exact replay, source non-restart after relinquishment, target generation, no dual writer, retained offline-Member convergence, one-claim receipt scrubbing, and cleanup of only exact operation-owned staging.
- Ordinary UI, internal composition and test drivers may invoke only complete negotiated operations. Unsupported transfer states stay visible as recovery/unsupported results, never as ready capability or permission to reuse bootstrap effects.
