# Application Services

`src/app/` owns application-scoped state services and adapters used by the composition root. Features and providers access these capabilities through stable host and core contracts rather than importing the concrete plugin class.

## Dependency Direction

- `src/main.ts` is the concrete composition root. It constructs app services and wires core registries, providers, and features.
- App repositories, storage, and settings services depend on core contracts. They must not import chat views, feature controllers, renderers, or provider-native protocol implementations.
- `FeatureHost` is the feature-facing application boundary; user-facing features must not import `ClaudianPlugin` from `src/main.ts`.
- `ProviderHost` is the provider-facing application boundary; provider runtime code must not reach through it to chat views or feature controllers.
- Concrete provider imports are allowed only in composition and provider-default assembly. Do not introduce them into conversation, storage, or settings transaction logic.
- Existing Claude compatibility imports of app settings or storage are migration seams. Do not use them as precedent; move a shared contract into `core/` before creating another provider-to-app dependency.

## State and Persistence Boundaries

- `ConversationRepository` is the source of truth for Claudian's current in-memory conversation projection. Feature code must request conversation mutations through `FeatureHost` instead of mutating cached conversations independently.
- Claudian metadata and accepted-input ledgers are durable Claudian state.
- Provider session IDs, resume checkpoints, and opaque `providerState` may be interpreted only by provider snapshots or typed provider history/state helpers. Generic app code may store those opaque values but must not infer or rewrite their fields.
- Persisted tab workspaces are view-scoped shells owned by the chat feature. Application storage exposes the former plugin-global `AppTabManagerState` only as a one-time migration source; it must not become a second live tab-state authority.
- Only `TabWorkspaceMigrationCoordinator` may read or retire the legacy global snapshot. Normal startup does not preload metadata from it; the claiming view loads metadata for the shells selected by its restore policy.
- Legacy tab migration decisions use state actually delivered to live views. A live view's synthesized `getState()` output is not evidence that Obsidian restored a view-scoped snapshot; deferred leaves may contribute their serialized leaf state directly.
- Once the aggregate leaf declarations include any view-scoped snapshot, including a deferred leaf, the migration coordinator retires the legacy global snapshot so it cannot become eligible again after that leaf is removed.
- Before a view restores conversation-backed tab shells, the application conversation repository must adopt metadata for every conversation selected by the restore policy. Deferred history scanning remains responsible for all other sessions.
- `Conversation.modelRecoverySource` is a read-only native locator used only to recover missing historical model metadata. It must never be treated as a resumable provider binding, and a successful recovery or fresh provider session retires it.
- `Conversation.linkedContentPath` is an optional canonical Vault-relative file or folder path. The Vault root is not a valid Linked content target. It is creation-only identity: ordinary patches, live-object mutation, saves, forks after creation, and deletion must not replace or clear it. Only the repository's explicit Vault-rename rewrite may change it, including descendants for folder renames; deletion leaves the identity durable so presentation can report Missing content.
- `SharedStorageService.setTabManagerState()` plus legacy tab-state reads and cleanup must preserve unrelated plugin data.
- Settings changes must go through `SettingsCoordinator` or the application mutation APIs so persistence, rollback, provider reconciliation, and publication remain ordered.
- Provider model-option changes reconcile affected durable conversation selections through `ConversationRepository` before views refresh. Providers and features may publish the change but must not rewrite cached conversations themselves.
- Environment changes that can alter model options use the same provider model-option reconciliation boundary; direct model-selector refresh is not an allowed shortcut.
- Deferred metadata with a stored model that needs fallback is withheld until `ConversationRepository` persists and adopts the replacement. Safe model-less shells may remain incrementally readable for environment-invalidation coordination; they must not expose a synthesized fallback before its write.
- A model recovered from provider-native history is availability-reconciled before its single durable write and before callers may publish it as recovered.

## Invariants

- Failed settings persistence restores the pre-mutation in-memory settings snapshot.
- A post-commit publication failure is reported as committed state; it must not roll back data that was already persisted.
- Collab is opt-in and defaults disabled. Disabled startup and live-disabled state must not construct Collab, start the Vault Agent Runtime, restore a Host, probe Git, load SQL, discover LAN peers, or write Collab filesystem state. Disabling first closes feature admission, then hides presentation and drains the Runtime plus every admitted feature operation before closing `CollabFeatureService` and `ClaudianCollabService`; durable Project, credential, repository, Ticket, request, and Host auto-start state remains untouched.
- `CollabFeatureService` public async methods must declare admission explicitly at the facade. Do not restore method-name reflection or constructor-time method replacement. Operation-ID-only conflict reads are global because their Project identity is resolved from the durable conflict record; every request carrying a Project ID is active unless it is one of the explicit local Retired inspection/finalization/retry actions.
- `src/app/collab/index.ts` is the lazy composition entry used by `src/main.ts`; export only the Collab foundation, feature service, Project setup service, subcomposition factory, and their composition-facing types. Internal repositories, coordinators, lifecycle workers, and transport helpers use their owning modules directly.
- Lifecycle control routing has one exhaustive policy map. Leave authenticates active-or-left for idempotent replay but retains ordinary active admission; only Host-transition proof reads, Retire, and Host-transfer cancellation bypass active admission. Retirement acknowledgement remains terminal-responder dispatch. Do not duplicate these decisions in the HTTP router or hosted service.
- A Project-session operation that detects terminal Retirement stops its projection connection and enqueues convergence without awaiting convergence from inside that session. Retirement convergence closes and drains the Project session; synchronously awaiting it from a session-owned snapshot, event refresh, inspection, or mutation would self-deadlock. Projection reset detaches obsolete reads/subscription creation from current state but keeps their settlement owned by the session until close/drain. Ordinary Leave must await that drain before local cleanup; Retirement deliberately separates close from drain to avoid reentrant self-deadlock.
- Any durable membership change that replaces endpoint, CA, Git URL, authority kind, or development actor must invalidate the retained Project authority session after persistence succeeds. LAN Host address rebind owns that invalidation before it closes the superseded listener; reconnect and Cloud binding use the same projection-reset boundary.
- Plugin `onload` never awaits Collab construction, Git, SQL, or network work. When Collab is enabled, workspace layout readiness schedules nonblocking lifecycle and Host recovery. Recovery stages and Projects are failure-isolated: one unavailable Retire responder, Host transfer, Leave, acknowledgement, cleanup, or Host must not skip the others, and incomplete durable work retries with bounded backoff during the session. Without durable lifecycle work or a Host auto-start Project, ordinary startup performs no Collab Git, SQL, network, or filesystem-write work.
- When Collab is enabled, plugin `onload` starts the Vault Agent Runtime in the background without awaiting bind. Listener construction, deterministic port selection, `runtime.health.check`, `runtime.operations.list`, and `runtime.operations.get` must not initialize Collab; only a real `collab.*` operation may resolve the lazy Collab application port. The actual endpoint is runtime authority rather than persisted configuration, and shutdown closes and aborts the listener before closing `CollabFeatureService` or `ClaudianCollabService`.
- The Vault Agent Runtime registry is the sole authority for lightweight operation listing, exact operation descriptors, parameter decoding, access classification, and dispatch. Protocol v5 operation names, access classes, required parameters, result DTO meanings, and error/retry semantics are a compatibility surface; breaking changes require an explicit protocol-version decision and matching contract-test updates. Every Project-scoped operation requires an explicit Project ID. Project detail maps active Members explicitly and derives `managerMemberIds`/`managerCount` from their roles; it never exposes a representative Manager or private Manager-set generation. Request detail and file reads share the freshly prepared effective candidate/contribution review manifest; raw current-main-to-head differences are not an Agent file manifest. Request and Ticket detail expose bounded first comment/relation pages plus stable continuation operations; the Runtime never assembles an unbounded detail collection. Request file reads expose only the exact selected file. Other file reads likewise accept only an exact path from a freshly re-derived application review or conflict manifest. Selected writes delegate only to existing `CollabFeaturePort` commands under the current Member identity, preserve exact revision/OID preconditions and application idempotency, and never navigate UI. Project lifecycle is projection-only at this boundary: summaries may expose lifecycle, cleanup status, and retirement time, but no Leave, responsibility, Host-transfer, Retire, cleanup, lifecycle-operation identity, CA, or package method/data enters Runtime v5. The Runtime never exposes snapshot IDs, private working-tree/file hashes, internal file objects, binary preview bytes, credentials, or a generic filesystem/Git/database call. Decoded calls have a 30-second wall-clock deadline and serialized responses have a 16-MiB UTF-8 cap; timeout, client disconnect, unload, and late output remain fenced. Listener closure and read-handler settlement stay bounded, while application teardown retains Collab owners until every admitted write invocation settles rather than disposing live mutation dependencies.
- A Project setup failure before authority commit may remove only its generated staging state and provisional local records. Rollback removes the provisional authority before staging artifacts or discoverable records, so failed authority cleanup remains resumable. Recursive staging cleanup requires both an already-owned Projects-root marker and an exact Project/operation/purpose/child ownership marker; a generated-looking name alone never authorizes deletion, and an unmarked collision is preserved. Once the authority Project row exists, setup must preserve authority and expose recovery instead of inferring rollback across stores.
- A completed local Project path is usable only under a Claudian-owned Projects root and when the working repository's local `claudian.projectId`, `claudian.memberId`, and `claudian.personalRef` config exactly match membership. The guarded historical `workspace` root may be claimed once as an explicit migration; arbitrary non-empty roots are never adopted. Version-1 setup migration provenance remains durable until its validated staging clone is placed successfully.
- A Host Vault owns one persistent Collab CA and issues short-lived IP-SAN server leaves from it. A trusted Project may refresh its endpoint under that exact CA. A Host-transfer CA replacement is accepted only through one unique public proof-chain suffix from the exact pinned CA to the candidate CA, verified before any Member credential or origin rotation; an unexplained or forked same-Project CA remains blocking.
- Initial LAN trust performs a credential-free TLS probe, matches the invitation fingerprint to the presented CA, persists that CA, and then completes normal CA and IP-SAN validation before transmitting any invitation or Member credential.
- Collab invitation secrets and Member credentials are independent 256-bit values. They must never appear in URLs, process arguments, logs, events, user-facing diagnostics, or error context.
- Finalizing a local Retired Project may move a still-pending acknowledgement into the independently discoverable acknowledgement queue before removing the Project index/private directory. Startup retries that queue without restoring the Project to the panel and never mistakes its fallback retirement payload for an active local Retired projection; a separately discovered applied cleanup journal can therefore finish removal while acknowledgement remains pending. Successful acknowledgement or the 30-day terminal window scrubs its credential and removes the queue record.
- A successful explicit Host start persists auto-start intent, an explicit stop clears it even when the runtime is already stopped, and plugin unload releases runtime resources without clearing intent. Layout-ready background restoration retries enabled Host-owned Projects without blocking startup. Completed outgoing Host-transfer recovery finalizes already-deleted old authority from its local checkpoint and must not reopen SQL or require Host ownership. Host startup must recheck coordinator admission after every awaited recovery inspection before it installs a route or recovery owner; shutdown owns and drains both active and recovering transfer runtimes before database disposal. One exclusive Vault Host lock guards one private-IP HTTPS listener; that listener multiplexes only registered Projects and closes after the final Project stops.
- While at least one Project is hosted, a preferred-private-IPv4 change starts a same-CA replacement listener before retiring the old listener. Every hosted membership must persist the new endpoint before the listener becomes current; persistence failure preserves the old listener, attempts to restore prior records, and leaves the monitor available to retry. A temporarily missing interface marks the Host as needing attention without closing the still-reachable listener, and invitations and mDNS advertisements must always follow the current listener.
- The LAN listener dispatches both Project control routes and Git Smart HTTP routes from the same registered-Project set. A Project is not marked running until its receive policy, protected hook, cumulative storage check, and `fsck` pass. Host stop/unload synchronously makes routes unavailable and starts socket, Git-child, and listener teardown before awaiting durable invitation revocation; teardown is bounded and does not delete Project state.
- Pending Member credentials authorize activation and the later N3 initial-clone capability only. Snapshot, event, publication, and review control paths require an active membership, and termination must close registered Member resources.
- Manager and Host responsibilities are independent. The active Member-role set is the only Manager identity authority; there is no primary Manager. Promotion is additive, demotion/removal preserves at least one active Manager, and fresh Accept/Retire/administration authorizes any current active Manager. Manager promotion and last-Manager succession require an online target-addressed protocol acknowledgement before authority atomically consumes the offer; offers conflict only when they share a source or target participant, so disjoint Manager pairs may progress concurrently, and membership mutation cancels only offers related to the affected Member. Projection automatically persists and acknowledges an offer addressed to the current Member, or declines it when that Member has a pending offline Leave. The same projection reconciles a response-lost acknowledgement and removes the local receipt once authority no longer projects that offer, so stale receipts cannot block later succession. This acknowledgement is not a second user confirmation. Host transfer requires explicit target acceptance and never follows Manager-role changes implicitly. An accepted Host-transfer response uses a stable operation identity and schedules outgoing recovery when the response either finishes or disconnects, so response loss cannot strand a durable acceptance. Before Cancel clears the authority-owned receiver credential, the source must durably reconstruct the exact outgoing recovery record; a recovery write failure leaves authority acceptance/cancellation state unchanged. Member leave/removal deletes pending relations for its discarded request and structured Ticket mentions targeting that Member, then commits credential termination, open-request discard, event, and idempotency result together; the Markdown containing an exited Member's `@` token remains unchanged, and the resource-revocation hook runs only after authority state is durable and must be idempotent.
- Individual Leave, Project Retire, and local cleanup are separate durable phases. Only an ordinary Member may queue Leave while authority is unavailable; Manager and Host departure require online authority decisions, and a Host cannot leave until Host transfer completes. Manager-responsibility acknowledgement, snapshot receipt reconciliation, and both Leave eligibility checks share one app-owned per-Project serializer. Leave releases that serializer before taking a token-owned temporary Project-work suspension, then reacquires it to re-read the durable local role and receipt immediately before cleanup. A pre-cleanup rejection may resume only the still-current suspension token; terminal Retirement permanently invalidates that token, while successful cleanup consumes it as permanent local closure. Online projection persists the raw snapshot cache first, then the role/cursor, and only then reconciles or retires the responsibility receipt. A non-last Manager leaves directly; only the last Manager needs an acknowledged successor offer, which authority consumes atomically with departure. Before Leave mutation, the exact expected Host and nullable legacy-Manager fingerprint plus accepted offer are durable; lost-response recovery first replays that tuple directly instead of requiring an active-member snapshot. A committed Leave whose post-commit resource cleanup needs recovery must retain that exact replay tuple and remain `recovery-required`; a revoked credential can no longer reconstruct it from an active snapshot. If Host movement or transfer makes the tuple stale, recovery verifies one public Host-transition proof chain and durably replaces the pending Leave's Host endpoint, certificate, and fingerprint before any credentialed read or mutation against the new Host; only then may it refresh authority state and retry the mutation. Keep/Delete cleanup begins only after the authority result or durable ordinary-Member queue record; Keep removes the exact verified Project `.git/` and local Collab state while preserving visible files, Delete removes the exact owned Project root, and neither choice may roll back membership state. Git detach and marker removal each have a pre-mutation durable checkpoint so restart never guesses from a missing path. Once a pending Leave records `localCleanupComplete`, later authority settlement/private-state purge must not resolve Native Git. Retired Keep/Delete retains its applied-choice journal until projection finalization and acknowledgement handoff are durable; startup discovers an applied journal independently from the Project index and removes it only when no Project, retirement record, or pending Leave can still own it. After local cleanup, an offline Leave retains only its independently discoverable settlement record; authority confirmation purges it, while terminal Retirement consumes it as the seed for the single Retired projection and acknowledgement path.
- Host transfer uses one durable operation identity from offer through completion. The target remains provisional until the exact old-CA-signed activation certificate matches its staged manifest; a restart after staging restores that same provisional route and operation-owned staging. Before an accepted response is returned, the source persists matching outgoing recovery; Accept and Cancel serialize around that checkpoint. A pre-cutover terminal result retains the target receiver credential until authenticated target cancellation is durably checkpointed; only then may old-Host admission reopen and the recovery record be removed. Before target cleanup, a hash-only terminal receipt is durable while exact staging ownership remains; cleanup completion then drops staging identity but keeps cancel/complete replayable until explicit source confirmation or its 24-hour bound. Raw receiver credentials never remain in either receipt phase. Authority relinquishment is the one-way fence: after it commits, the old active route never reopens and recovery may only resume toward target activation. Vault CA private keys and receiver/Member credentials never enter packages, URLs, logs, events, process arguments, or diagnostic context.
- Retire is a terminal authority transition, not a sequence of Member leaves. A discoverable tombstone is the point of no return: any later authority/checkpoint failure must activate terminal recovery and must never reopen active admission. Terminal activation and active-authority teardown never wait for best-effort client delivery or local cleanup success. Confirmation, operation-response replay, event, and terminal fallback enter one client handler that first persists Retired, then acknowledges and drains/de-initializes local Git; startup also treats a durable retirement record beside an Active index entry as an incomplete Retired transition. Retired projection, retry, Keep, and Delete remain available without Native Git; their local repository-identity verifier reads only the bounded, non-symlink `.git/config` Claudian identity fields and never launches Git. Retirement acknowledgement retries are lifecycle-owned, cancellable, drained on shutdown, and use bounded exponential backoff. Rediscovery may retry the same endpoint only after public proof-chain verification establishes its new CA, before any Member credential is transmitted. The active authority is replaced by a minimal authenticated responder and public Host-transition chain for the complete 30-day recovery window, so even the final acknowledgement remains replayable after a lost response; responder expiry never removes a device's local Retired projection or visible files.
- An online coordination snapshot projects both the current Member role and monotonic event cursor into local membership after the cache is durable. `updateMembershipProjection` is the sole local mutator for that pair; do not reintroduce a cursor-only projection path. Host composition of membership state with lifecycle summaries must fence the read with matching authority event sequence and Manager-set generation; a concurrent mutation retries instead of returning a mixed snapshot. A lower snapshot sequence is rejected before cache, role, cursor, or Manager-receipt mutation, and a snapshot for another Member identity is an integrity failure.
- LAN Project-control JSON and event routes are uniformly versioned at `/v9/projects/` and reject other Project-control versions before body read, authentication, admission, or authority dispatch. Git Smart HTTP remains independently stable at `/v1/git/`, while the credential-bound provisional Host-transfer recovery channel remains independently frozen at v6; never couple these three version authorities. Control route modules consume the exhaustive binding policy and never become SQL or Git owners.
- Git Smart HTTP routes become reachable only after the exact bare repository receives Host-managed receive policy and protected-ref hook, remains below its cumulative storage limit, and passes strict `fsck`. Native `git-http-backend` owns the wire protocol; Claudian validates the fixed route, authenticates Basic credentials again after asynchronous admission work and immediately before child registration, bounds receive input by remaining storage, streams CGI with backpressure, and owns every spawned child through disconnect, timeout, and Host stop.
- Pending Members may use upload-pack only for their initial clone. Receive-pack requires active membership, passes only Host-authenticated Project/Member/ref identity to the child environment, and the pre-receive hook permits exactly one non-deleting fast-forward update to that Member's personal ref. Member credentials never enter the child environment.
- Expiring a pending Member deletes its prepared personal ref only when it still equals canonical main. A missing ref is already clean; any divergent or concurrently changed ref is retained and surfaced for diagnostics rather than deleted.
- Join persists its attempt before network access and advances monotonically through trusted, membership-created, clone-completed, placed, and activated phases. The encoded invitation is retained only until a Member credential is durably available; after that boundary, failures preserve resumable private state instead of inventing rollback of Host membership.
- A joined working copy becomes visible at its final `workspace/<slug>` path only after the staged clone proves the exact personal branch, clean index/checkout parity, portable regular-file paths and limits, and strict repository integrity. Placement is an atomic same-container rename; cancellation, retry, or remote membership failure never deletes an already placed working copy.
- Member reconnect accepts either a fresh invitation or bounded mDNS candidates for the selected Project. mDNS advertises only protocol version, Project ID, endpoint, and CA fingerprint; it is never a trust or credential channel, discovery failure preserves manual reconnect, and Host startup remains successful when advertisement is unavailable. Same-CA candidates are independently proved under stored trust and active-Member endpoint confirmation. A different-CA candidate is considered only through explicit Host-transition discovery and one exact public proof-chain suffix; proof verification precedes construction of a credentialed client. Multiple confirmed endpoints, a proof-chain fork, or a confirmed endpoint alongside an authority rejection is blocking. Reconnect accepts only an exact old-to-new generated same-Project `origin` transition, persists trust and endpoint only after confirmation, and resets endpoint-bound clients only after persistence succeeds; Host-owned Projects restart hosting instead of reconnecting as Members.
- Every valid local Project has required versioned publication state containing `baseMainOid` and at most one exact in-flight operation. Operation `phase` is the sole durable confirmation authority: `captured` has null candidate/current-main OIDs, and every later phase has both OIDs. It stores OIDs and phases only, never mirrored confirmation flags, credentials, absolute scratch paths, or file contents. Publish commits a dirty snapshot at most once, persists an exact current-main/candidate confirmation before mutation, never force-pushes or silently resets a personal ref, and invokes idempotent request ensure only after the confirmed local head is exact on that Member's Host ref.
- A Project may also have one private `request-draft.json`. It stores only the complete description plus request/head/revision synchronization coordinates, is written before Publish mutates Git, survives offline/recovery failures, and is removed only after Host acknowledgement matches the exact description and head. It never stores a parallel Ticket-relation selection; relations are always re-derived by the Host from description syntax.
- **My changes** is a read-only virtual-squash review from the current Member's last authoritatively Published open-request head to the present personal working result, including later local commits plus index, worktree, and untracked changes. When online authority has no usable request head, the personal remote-tracking head is the fallback, then current `HEAD`; deriving this review must never move a ref or mutate the index. Publication candidate review remains a separate exact current-main-to-candidate confirmation and must not supply the sidebar's personal file list.
- Networked Publish and review require the configured `origin` URL to equal the current trusted membership URL before a runtime-only credential is exposed. A Host-owned clone may repair the generated stopped-Host placeholder or a generated same-Project HTTPS LAN IPv4 URL after its Host address changes; arbitrary, cross-Project, and non-IP origin changes remain blocking.
- Publication probes the pinned authenticated control plane before exposing a Git credential. Background accepted-state writes are limited to contribution-free fast-forward; divergent or conflicting candidate application belongs only to exact Contributor-confirmed Publish. Every path revalidates worktree, index, refs, publication state, membership, and Git locks at its write boundary.
- `GitRepositoryService` may reuse canonical repository validation only inside an explicit, callback-bounded read session. Such a session exposes no mutation API and expires when its callback settles; credential exposure, repository mutation, and final write-safety checks require fresh validation. Review presentation may batch exact refs, changed-object metadata, and selected blobs, but admission, request ensure, Accept, and recovery retain complete reachable-tree validation. Review preparation may skip a network fetch only after validating the exact origin and proving that local remote-tracking refs satisfy the fresh authoritative request OIDs; otherwise it must fetch and revalidate before rendering.
- The Project-local Git CA file is reusable public trust material derived from the currently persisted membership CA. Every network operation must still revalidate membership, origin, authenticated control reachability, and the CA contents before exposing a runtime-only credential; Member credentials never enter the CA file or another durable Git helper.
- `CollabFeatureService` query operations such as Project inspection do not publish feature state. Explicit refresh and mutation paths own publication because presentation subscribers may issue queries, and query-triggered publication creates reentrant refresh loops.
- New Create and Join operations capture the normalized Vault-relative Projects folder in durable pending state. Startup and resume discover those documents from their owned Project directories independently of the Project index; an absent or stale index is never evidence that no operation exists. Every staging, clone, final-placement, cleanup, and recovery path derives from the captured root; settings changes never redirect pending or completed Projects. `CollabWorkspaceService` alone claims a Projects root through its versioned ownership marker and parent-Git guard, and it rejects unrelated non-empty or symlinked roots before generated writes.
- Initialization, Project selection, successful Accept, and typed accepted-main invalidations register accepted-state synchronization through `CollabFeatureService`; publication events never start reconciliation directly. Initialization and selection register it before publishing ready or newly selected state, but the ready shell does not wait for maintenance to finish. Selection may inspect a resumable conflict first, but must not notify presentation subscribers until synchronization is registered. Comment, request-only, membership, and ordinary presentation invalidations do not schedule Git mutation. Event connections still refresh the authoritative snapshot on every open or reconnect and resume from the durable sequence cursor.
- Project inspection and accepted-state synchronization form a Project-scoped read/write fence: scheduled synchronization waits for inspections already in progress, while later inspections wait for that synchronization before reading conflict, Git, and publication state. Never combine a pre-synchronization Git snapshot with post-synchronization publication state. Aborting or replacing a synchronization does not release its fence; retain that Project's task until the underlying work settles. Disposed or superseded lifecycle continuations must not restart Git work.
- Accepted-state synchronization may fetch while a contribution exists but must not merge, push, update a request, or change visible files. Only a clean personal head that is an ancestor of accepted main, with no dirty index/worktree, local/offline progress, open request, publication recovery, or conflict recovery, may fast-forward and synchronize its personal ref.
- When a matching open request conflicts with newly accepted main, background analysis may persist the exact captured publication operation and scratch conflict session so the Contributor sees **View conflicts**. This is read-only with respect to the visible working tree, personal Host ref, and request; clean open-request divergence remains Manager-owned at Accept.
- Contribution-free fast-forward may update only the checked-out current Member branch after exact clean-worktree, symbolic-HEAD, personal/main/remote-ref, publication-record, and Git-lock revalidation. Concurrent change aborts the automatic mutation. Conflicting analysis is read-only and must never place raw conflict markers in the visible Project.
- Repository hooks are suppressed only for Claudian-owned local accepted-state merge commands. Do not disable hooks globally: Host receive-pack relies on the managed `pre-receive` hook as its final protected-ref boundary.
- Conflict recovery persists immutable starting OIDs and derives every absolute scratch path locally. Native Git conflict index stages are authoritative; raw markers remain confined to the disposable private clone.
- Conflict-file presentation reads base, personal, and accepted versions from the immutable starting commits rather than the mutable conflict index. Binary reads expose only existence, path, and size metadata to feature code. Native Git `merge-file --diff3` supplies stable text segments for Agent reads; feature presentation renders the complete personal-versus-accepted file without interpreting diff DOM.
- Conflict presentation is read-only. The Contributor or Agent edits the real Project files, and the next explicit Publish commits that local result. Scratch preparation then treats the new personal result as authoritative for remaining conflict entries, creates a retained exact candidate for full Contributor review, and preserves an existing request identity. Only persisted **Confirm and Publish** intent may revalidate, fast-forward the current Member branch, push it, and update the request.
- Local conflict fetch, ref cleanup, and merge commands suppress repository hooks per command. Successful or crash-recovered conflict finalization must not reset visible work or rewrite the personal ref; its operation-scoped publication candidate remains retained until exact Confirm and Publish cleanup.
- Request ensure rechecks active membership, requires the submitted OID to be the exact current Host personal-ref head and Host main to equal `expectedMainOid`, validates every reachable tree entry, and then persists the request mutation, redacted event, validated main, and idempotency response in one authority transaction. A matching replay rechecks membership but returns before Git validation; a reused key with a different Project/head/expected-main fingerprint is always rejected.
- Accept requires an active Manager and one exact open request/main/head/personal-ref tuple. It uses `merge-tree`, validates the complete merged tree against the same portable regular-file and checkout quotas used at admission, creates a Claudian-identity commit with `commit-tree`, and applies it through CAS `update-ref`; it never checks out or rewrites a Member ref. Recovery repeats full-tree validation before any pending main-ref transition. Once an Accept operation is incomplete, request ensure cannot mutate that request and no resolving Ticket may change content, status, comments, or revision until recovery completes.
- Accept is online-only and requires a freshly synchronized authority snapshot even when the acting Manager and Host are different Members. The mutation carries the exact request revision and resolving-Ticket revision set; authority rejects any metadata, relation, Ticket, main, or head drift. Finalization promotes accepted commit relations and closes only the exact accepted `resolves` set; `references` remain open.
- `accept_operations.prepared` means the exact request is durably locked with no result OID. `ref_updated` means the result OID is durable and the main-ref transition may be either pending or already applied; recovery must inspect main, retry only from the expected OID, finalize when main equals the result, and disable further Accept when main is neither. Request completion, redacted event, and idempotency response are one authority transaction.
- Authority mutation observers run only after the committed SQLite image is durably promoted. WebSocket events are monotonic redacted invalidations, never authoritative state; sequence gaps and unknown event kinds require a fresh snapshot.
- Request comments are immutable normalized Markdown attached to an open Request as a whole. They appear chronologically in the Request Overview, never carry file, line, diff-side, or snapshot identity, and no comment content enters event payloads. Terminal Request history remains readable but cannot receive new comments. The current authority schema contains no line-anchor representation.
- Tickets have no assignment state. Ticket descriptions and comments expose `@<display-name>` syntax, while Authority resolves only an exact, unambiguous active-Member display name and persists the stable target Member ID; ambiguous, escaped, code-fenced, and unknown names remain plain text. Description edits replace that source's mention set, immutable comments append their own set, and Member termination removes the target's structured mentions without rewriting Markdown. Mention records are private authority state until a separate query contract is intentionally added.
- Review data is derived again from exact fetched main and Member OIDs. Clean requests compare main to the candidate merge tree; conflicting or stale requests compare merge base to the reviewed head. File contents are read only for the selected path, and raster preview requires both a supported extension and matching file signature.
- Client `cache.json` is a validated stale-read projection only. It may retain bounded exact-query Ticket-list pages and finite complete cursor-free Ticket details for explicit offline read-only rendering, but never mutation state or incomplete detail pages. Runtime first-page and continuation-page detail queries remain online-only and must never synthesize a bounded result from complete cache. Online reads remain authoritative, the membership event cursor advances only after the coordination projection is durable, and authorization or integrity failures must never fall back to cached state.
- Conversation persistence for one conversation remains ordered, and stale execution snapshots must not overwrite newer provider state.
- Deletion, hydration, and execution-snapshot writes must preserve their existing generation and binding fences.
- Archiving clears pin state, cannot be inferred from tab closure, and never mutates provider-native history.
- Historical model recovery is best-effort, concurrency-bounded, provider-owned, and must not overwrite a model selected or recovered by a newer operation.
