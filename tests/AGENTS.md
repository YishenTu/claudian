# Test constraints

- Use package test commands: `npm run test:unit -- <path>` runs either a unit or integration Vitest file with the required Node local-storage option. `npm run test` also runs script/architecture/config checks; targeted Vitest does not.
- Before adding a test, inspect coverage of the behavior across unit and integration suites, not just the changed module's test file. Identify the observable contract and a plausible regression existing coverage misses. If an existing test catches it, use that test for before/after verification without adding a case. Otherwise extend the case or table that owns the contract; additional test layers need a distinct failure mode.
- Choose the test boundary from the intended behavior and plausible failure, rather than the function or file being changed. Exercise the real components needed to establish that behavior, and assert the observable result at the relevant boundary. Isolated tests of individual steps do not establish that those steps work together.
- Prefer focused integration tests for behavior spanning multiple components. Use unit tests for self-contained contracts and detailed edge cases; use broader or real-environment tests when the relevant failure cannot be reproduced within the integration boundary. Place suites by what they run: `tests/unit/` exercises one module with external dependencies stubbed; suites running several owned modules, or a real filesystem, process or DOM interaction flow, belong in `tests/integration/`.
- When adding a higher-layer test, or when branches, callers, ownership, or dependencies change, revisit the affected coverage. Consolidate redundant proof, including lower-layer cases the new test supersedes, and remove support made obsolete by the change; keep this maintenance within the affected area.
- Tests must exercise the behavior they claim; mocks must not supply the transformation, persistence, admission, or ordering being asserted. Do not assert state or DOM relationships established entirely by fixture construction or mock callbacks. Integration tests keep interacting owned modules real; use narrow public ports only for environment, Obsidian, provider, or other dependencies outside the behavior under test. Unit tests stub only external or nondeterministic dependencies; needing to mock an owned collaborator means the behavior spans both modules and belongs at the integration boundary.
- Each external boundary (Obsidian, the provider host, each provider's native peer) has one authoritative test fake under `tests/__mocks__/` or `tests/helpers/`. Extend it when a test needs missing behavior instead of adding a parallel fake, local DOM model or per-file module override; per-file overrides are for test-specific faults or malformed input. Fakes of an external host match its supported implementation: they neither add semantics it lacks, such as labels, roles or completion signals, nor drop behavior it has, such as callback re-entry. Native peers stay provider-owned even when protocols look alike.
- Type fakes, hosts and ports against their production contracts so contract drift fails typecheck; capabilities a fake does not model throw when used instead of silently succeeding. Casts are for deliberately malformed input.
- Assertions must distinguish correct behavior from the relevant fault, with independently grounded expected results. Negative fixtures must reach the intended guard; asynchronous assertions must observe the lifecycle point where the failure could become visible. Inside callbacks the code under test may catch, record observations and assert them after the call returns. When a debounce, timer or retry could also produce the asserted effect, hold it so only the step under test can. For UI absence checks, establish that the relevant surface rendered and the query still addresses the current control or state. If a stale query could pass unnoticed, verify it detects an injected forbidden control or state.
- Optional method presence, copied option arrays, configuration values passed to collaborators, private markup and call sequences are not contracts by themselves; assert their effect, such as the behavior when a deadline expires. Assert the behavior through real consumers when they already cover the same contract; retain direct checks when they protect a distinct compatibility, protocol, lifecycle or performance requirement.
- Before removing or consolidating coverage, identify retained proof for each meaningful assertion or establish that the behavior is retired. Carry missing assertions into the keeper first. Passing tests alone do not establish equivalent coverage; use a targeted fault check when equivalence is uncertain. Absence of repository-local callers is insufficient to retire an externally reachable plugin or compatibility contract.
- Preserve coverage for distinct protocol, platform, security, lifecycle, persistence, and compatibility failures. Consolidation must retain assertions that distinguish those failures. Small tests and static checks are not deletion candidates merely because of their form.
- Do not add production facades solely for testing, or APIs or state solely to expose implementation details to tests.
- Express fixture timestamps with `@test/helpers/testClock`, which captures a current-time baseline for each test module environment. Derive related creation, expiry, and assertion dates from that timeline; share one injected clock across interacting services and advance it explicitly for expiry tests. Do not add fixed calendar anchors. CI also runs selected Vitest tests about three years ahead under libfaketime.
- Shared provider changes need neutral-contract coverage and distinct native adapter cases.
- DOM interaction and accessibility regressions need real-DOM tests with Testing Library role/name queries and targeted `axe-core` checks. Isolated controller logic may use unit tests without a DOM; `MockElement` class/tag assertions do not establish accessibility or keyboard behavior.
- CSS assertions need a functional, compatibility or explicit design requirement; copying current spacing, color or selector literals is not sufficient. jsdom computed styles can check declarations and state changes, but do not prove rendered geometry or contrast. Use rendered measurements or a repeatable host reproduction for those claims, while retaining narrow host-compatibility and functional-state checks.
- For regular PR/push cross-platform smoke, real-process tests run on macOS/Windows only when listed in `crossPlatformTests` in `scripts/testSuites.cjs`; the Windows Pi launch test has its own CI step. Scheduled verification runs the full Vitest suite on macOS and Windows, with Windows sharded into three jobs and subject to individual test and platform skips. Linux results do not prove process or launch behavior. When coverage leaves a listed file through a rename, split or move into another suite, list every file that now holds it; unlisted destinations silently lose that smoke coverage.
- Tests that read source files through `fs` (CSS, locales, captured fixtures) are invisible to Vitest's graph; register them in `fileConsumers` in `scripts/ciTestSelection.mjs` (suites under `tests/unit/style/` are listed automatically) or CI and `test:affected` skip them. Type-only importers are intentionally outside runtime-related selection; typecheck covers their contracts.

- VM threads isolate module graphs and globals, but reuse process-level state between files. Restore mutated `process.env`, working directories and native module state. If a test needs unsupported thread operations or a native cache/realm/process lifetime, add a documented exception to `processFiles` in `vitest.config.mts`; verify both ordinary and shuffled full runs. Do not disable isolation to improve timing. Tests must also pass in any order within a file; nightly CI shuffles files and tests. `vi.clearAllMocks()` keeps implementations: a test that overrides a shared mock's implementation must restore it, or `beforeEach` must reinstall the baseline. Dispose mounted surfaces after each test; their document-level listeners otherwise handle the next test's events.
- Synchronize on the event, barrier or fake-timer advance that marks the lifecycle point under test. Real sleeps, polling loops and fixed counts of microtask flushes may only bound a missing signal, never order the test. A fake peer's own scheduling does not show that the client reached a state; release peer events from an observed client step.
- Split a file whose tests each start real processes or servers by contract into siblings sharing one fixture module once it dominates suite wall time; a file runs serially in one worker. Keep per-test process isolation.
- Fake timers leave `nextTick` and `queueMicrotask` real unless explicitly selected. Forks cannot fake `nextTick`; choose timer controls that preserve the asynchronous boundary under test.
- Native ESM namespace exports are not writable. For builtin spies, use a forwarding `vi.mock` namespace and ensure production and the test import the same mocked namespace.
